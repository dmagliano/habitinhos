# Phase 06.3 Context

## Phase Boundary

This phase closes the access-recovery gap before Phase 7 demo polish:

- Password reset by email for registered responsible users.
- Responsible PIN reset by email for authenticated responsible users after password verification.
- Account deletion/deactivation from the responsible mobile area.
- Mobile CTAs and screens that expose these flows naturally from the places where users enter password/PIN.

Email provider selection is intentionally outside this phase's product decision surface. The backend now has an email sender abstraction and a Resend sender may be configured through environment variables, but the phase must keep the domain flow provider-agnostic at service/controller boundaries.

## Current Code Findings

### Mobile

- `mobile/src/features/auth/LoginScreen.tsx` has the `Senha` field and login action, but no `Esqueci minha senha`.
- `mobile/src/features/auth/ResponsiblePinPrompt.tsx` has the `PIN do responsável` field and confirm/cancel actions, but no `Esqueci meu PIN`.
- `mobile/src/features/auth/RegisterScreen.tsx` creates password and PIN. Recovery links should not appear there because the user is creating, not recovering, credentials.
- `mobile/src/features/auth/authService.ts` only exposes login, register, responsible PIN verify, and `/me` session loading. It does not expose reset/delete methods yet.
- `mobile/src/navigation/routes.ts` does not include password reset, PIN reset, or account deletion routes.

### Backend

- `backend/src/main/java/br/com/habitinhos/auth/AuthController.java` currently exposes register, login, responsible PIN verify, and `/me`.
- Reset and delete endpoints are not currently wired in `AuthController`.
- `AccountEmailSender` has welcome/password-reset/PIN-reset methods in the worktree; execution must connect these to real service flows without leaking reset tokens in API responses.
- Existing auth/service patterns use server-derived tenant context, soft deactivation, validation DTOs, Spring integration tests, and OpenAPI coverage.

## Locked Decisions

- Password reset request must return enumeration-safe feedback: do not reveal whether an email exists.
- Password reset confirmation uses an emailed code/token plus a new password.
- Responsible PIN reset is an authenticated responsible flow and must verify the account password before sending the reset email.
- Responsible PIN reset confirmation uses an emailed code/token plus a new 4-digit PIN.
- Account deletion should be implemented as soft deactivation, consistent with existing history-preserving decisions. Historical missions, rewards, transactions, and redemptions must remain query-safe.
- Do not show recovery CTAs on registration.
- Recovery emails can include raw one-time codes/tokens, but only hashed tokens should be persisted.
- Token expiration, single-use semantics, and invalidation of older active tokens are required.

## UI Entry Points

- Login password field: add `Esqueci minha senha`.
- Responsible PIN prompt: add `Esqueci meu PIN`.
- Responsible profile/settings area: add deliberate account deletion entry point.

## Non-Goals

- No email confirmation before account creation.
- No child-auth redesign.
- No push notifications.
- No provider-specific template management in the UI.
- No hard deletion of historical family records.

## Open Implementation Notes

- If the backend reset-token schema already exists in the worktree during execution, reuse it. If not, add a Flyway migration for hashed token, purpose, expiration, and used timestamp.
- The mobile should prefer full-screen flows for reset request/confirm because these are multi-step, keyboard-heavy forms.
- The account deletion UI can be a settings/profile section plus confirmation modal/screen; it should avoid accidental one-tap destructive behavior.
