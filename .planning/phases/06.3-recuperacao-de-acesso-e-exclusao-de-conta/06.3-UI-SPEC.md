# Phase 06.3 UI Spec

## Design Intent

Recovery should feel calm, private, and unsurprising. The user is likely blocked or anxious; the UI should give short, concrete next steps without exposing account existence or technical token details. Keep the existing Habitinhos visual language: quiet cards, PT-BR copy, familiar form controls, restrained secondary links, and explicit destructive confirmation for deletion.

## Screen Requirements

### Login

- Add a text-style secondary action `Esqueci minha senha` near the password field or below the login actions.
- The action must be visually discoverable but not compete with `Entrar na conta`.
- Pressing it opens `AuthPasswordResetRequest`.
- Keep `Mantenha-me conectado`, login errors, and `Entrar na conta` behavior unchanged.

### Password Reset Request

- Title: `Recuperar senha`.
- Field: email, labeled `E-mail`.
- Primary action: `Enviar instruções`.
- Secondary action: `Voltar para entrar`.
- Success copy must be enumeration-safe: `Se o e-mail estiver cadastrado, enviaremos as instruções.`
- Do not reveal account existence through error text.
- After success, show a path to `Informar código` and a path back to login.

### Password Reset Confirm

- Title: `Criar nova senha`.
- Fields:
  - `Código recebido`
  - `Nova senha`
- Primary action: `Salvar nova senha`.
- Secondary action: `Voltar para entrar`.
- On success, show concise feedback and navigate or offer navigation back to login.
- Invalid/expired code uses backend-provided friendly copy, e.g. `Código inválido ou expirado.`

### Responsible PIN Prompt

- Add a text-style secondary action `Esqueci meu PIN` below the PIN input and before confirm/cancel actions.
- Pressing it opens `ResponsiblePinResetRequest`.
- The existing `Confirmar PIN` and `Cancelar` actions remain stable.

### Responsible PIN Reset Request

- Title: `Recuperar PIN`.
- Explain that the responsible password is needed before sending the reset code.
- Field: `Senha da conta`.
- Primary action: `Enviar código`.
- Secondary action: `Cancelar`.
- On success, show `Enviamos as instruções para o e-mail cadastrado.` and a path to `Informar código`.
- Wrong password uses the existing credentials error style.

### Responsible PIN Reset Confirm

- Title: `Criar novo PIN`.
- Fields:
  - `Código recebido`
  - `Novo PIN`
- `Novo PIN` must accept exactly four digits and use numeric keyboard.
- Primary action: `Salvar novo PIN`.
- Secondary action: `Cancelar`.
- On success, close the reset flow and return to the PIN prompt or responsible area with clear feedback.

### Account Deletion

- Entry point belongs in the responsible profile/settings area, not in child mode.
- Use a clearly destructive label: `Excluir conta`.
- Confirmation must require deliberate action. Preferred pattern:
  - Explain impact in plain PT-BR.
  - Require current password or an explicit typed confirmation if backend chooses password elsewhere.
  - Primary destructive action: `Excluir minha conta`.
  - Secondary safe action: `Cancelar`.
- After success, clear the local session and return to unauthenticated welcome/login.

## Accessibility

- All new actions must be queryable by visible text and role where applicable:
  - `Esqueci minha senha`
  - `Enviar instruções`
  - `Salvar nova senha`
  - `Esqueci meu PIN`
  - `Enviar código`
  - `Salvar novo PIN`
  - `Excluir conta`
  - `Excluir minha conta`
- Inputs must have explicit `accessibilityLabel` values matching visible labels.
- Error/success messages must be visible text, not only console/log output.

## States

- Loading state disables duplicate submits and changes primary labels consistently, e.g. `Enviando...`, `Salvando...`.
- Network/API failures use the existing friendly `ApiError.userMessage` mapping.
- Request success does not auto-fill or expose codes.
- Confirmation success clears sensitive form fields.

## Non-Goals

- No visual redesign of auth screens.
- No in-app display of email templates.
- No recovery links on registration.
- No child-facing account deletion.
