<domain>
## Phase Boundary

Phase 06.1 captures post-UAT corrections discovered after running the app with
the completed Phase 6 responsible flow. It refines the app entry experience,
session persistence, child/responsible mode switching, dashboard navigation
affordances, and delivered reward-redemption tracking.

This phase should not absorb Phase 7 demo seeds, README/docs, architecture
documentation, presentation script, or broad final polish. Phase 7 remains the
TCC demo readiness pass after these functional corrections land.

</domain>

<decisions>
## Implementation Decisions

### Entrada e autenticação
- **D-01:** When the user is not logged in, the app must show a welcome entry
  screen instead of immediately showing a login form.
- **D-02:** The unauthenticated entry must offer Login and Registro options.
- **D-03:** The login flow must include an explicit "mantenha-me conectado"
  checkbox/option.
- **D-04:** Token persistence must follow the "mantenha-me conectado" choice.
  If the user does not opt in, the session may stay in memory for the current
  runtime but must not be restored after app restart.
- **D-05:** Registration should reuse the existing backend `POST /auth/register`
  endpoint and the same authenticated session shape returned by login.

### Troca de modo criança/responsável
- **D-06:** After entering the child flow, the app should not show the
  mandatory "Sou responsável" / "Sou criança" hub as the normal transition.
- **D-07:** Child mode must expose a clear "Gerenciar família" action that
  enters responsible family management.
- **D-08:** Responsible mode must expose a clear return path to child mode,
  with copy equivalent to "Voltar para o modo criança" when a child context is
  known.
- **D-09:** Mode switching is navigation/UX state only. Backend authorization
  remains derived from the authenticated responsible user's JWT/family context.

### Dashboard e resgates
- **D-10:** The dashboard approval card/box must open the dedicated pending
  approvals screen.
- **D-11:** The dashboard recent-redemptions card/metric must open or scroll to
  the recent redemptions section.
- **D-12:** Each recent redemption card must show an "Entregue" checkbox.
- **D-13:** When "Entregue" is checked, the state must be persisted in backend
  reward-redemption history, the card text must render greyed out, and the UI
  must show `Entregue em: {data}` using the persisted/current delivery date.
- **D-14:** Delivered redemption tracking is a fulfillment state. It must not
  create a second wallet debit, alter coin ledger history, or cancel a
  redemption.

### the agent's Discretion
- Exact route names, component boundaries, and whether welcome/login/register
  are one screen with mode tabs or separate stack screens are left to planning.
- Exact PT-BR copy can be improved as long as the visible intent remains clear.
- The planner should decide whether recent redemptions are navigated to by
  scrolling, route param focus, or a dedicated screen, but the behavior must be
  testable.

</decisions>

<specifics>
## Specific Ideas

- Preferred copy for child profile management action: `Gerenciar família`.
- Preferred copy for responsible return action: `Voltar para o modo criança`.
- Recent redemption delivery text must be exactly testable in shape:
  `Entregue em: {data}`.
- Delivered redemption cards should keep existing reward title, child name, and
  cost, with greyed text after delivery.

</specifics>
