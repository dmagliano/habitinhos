# Phase 06.1: Ajustes pós-UAT dos fluxos de entrada, troca de modo e entrega de resgates - Research

**Researched:** 2026-06-03T10:01:44-03:00
**Mode:** Local codebase research
**Status:** Ready for planning

## Research Question

What needs to be known to plan the post-UAT changes safely without hiding
functional work inside Phase 7 demo polish?

## Executive Summary

Phase 06.1 should be planned as a small functional correction phase, not as a
quick task and not as Phase 7 polish. The requested changes span three surfaces:
mobile auth entry/session behavior, authenticated child/responsible navigation,
and backend-persisted reward-delivery state. The first two are mostly mobile
navigation and screen work. The delivered reward checkbox is cross-stack and
requires a database migration, backend endpoint/service behavior, DTO updates,
OpenAPI coverage, mobile service/types, and dashboard UI updates.

Primary planning recommendation: split into two or three focused plans. Keep
auth/mode switching separate from redemption delivery persistence so the
executor can verify navigation and backend state independently.

## Current Implementation Findings

### Auth entry and session persistence

- `RootNavigator` currently renders `LoginScreen` directly when unauthenticated
  and renders authenticated stack routes when `session && status ===
  'authenticated'`.
- `LoginScreen` is currently a login-only form with brand/supporting copy,
  fields `E-mail` and `Senha`, and submit `Entrar na conta`.
- `AuthContext.login(email, password)` always persists the token through
  `tokenStorage.setToken(loggedSession.token)`.
- `tokenStorage` stores only one SecureStore key: `habitinhos.authToken`.
- `authService` exposes `login` and `me`; it does not expose mobile
  registration yet.
- Backend already supports `POST /auth/register`, returning the same
  `AuthResponse` shape as login.

Planning implication: add an unauthenticated entry route/screen and a register
screen or auth-mode screen in mobile only. Extend `authService` and
`AuthContext` with registration. Change login persistence to accept a
`rememberSession` boolean. For unchecked "mantenha-me conectado", keep the
session in React state but skip SecureStore persistence.

### Authenticated mode switching

- `FamilyHubScreen` currently shows both `Sou responsável` and `Sou criança`.
- `RootNavigator` registers `FamilyHub`, `ResponsibleTabs`,
  `ChildProfileSelect`, and `ChildTabs`.
- `ChildTabsScreen` profile tab currently offers `Trocar criança`, `Voltar para
  família`, and `Sair da conta`.
- `ResponsibleTabsScreen` profile tab currently receives
  `onBackToFamily={() => navigation.navigate('FamilyHub')}`.
- Phase 4 explicitly chose `FamilyHub` as first authenticated landing, but the
  post-UAT finding supersedes that for the demo flow.

Planning implication: preserve `FamilyHub` only if still useful as a fallback
or transitional route, but stop using it as the normal mandatory mode gate.
The simplest child-first approach is:

1. Authenticated initial stack route opens `ChildProfileSelect` when no child is
   selected.
2. Selecting a child opens `ChildTabs`.
3. Child profile action `Gerenciar família` navigates to `ResponsibleTabs` and
   passes or stores the active child context.
4. Responsible profile action `Voltar para o modo criança` navigates back to
   `ChildTabs` with the active child when known; otherwise it should open
   `ChildProfileSelect`.

The planner should decide where active child context lives. A route param is
enough if the path always enters responsible mode from a child; a tiny
navigation/session context is safer if responsible forms navigate deeply and
need to preserve the return child.

### Responsible dashboard links

- `ResponsibleHomeScreen` already has `openApprovals()` and `ApprovalCard` with
  accessibility label `Abrir aprovações`.
- Recent redemptions are rendered as plain `Card` items at the end of
  `ResponsibleHomeScreen`.
- `getMetrics()` calculates a `Resgates recentes` metric, but metric cards do
  not currently navigate.

Planning implication: approval navigation is likely already correct, but the
plan should require a regression test proving the approval card opens
`ResponsibleApprovals`. Recent redemptions need either an interactive metric
card/card action, a route focus param, or a scroll-to-section behavior. The most
testable option is to make the `Resgates recentes` metric/card pressable and
focus/scroll to the recent-redemptions section, with a test asserting the press
causes the section to become targeted or visible through route/local state.

### Reward delivery state

- `RewardRedemption` currently has `status` defaulting to `REDEEMED`, plus a
  `cancel()` method that sets `CANCELLED`.
- `RewardRedemptionStatus` currently contains `REDEEMED` and `CANCELLED`.
- `V3__create_reward_schema.sql` creates `reward_redemptions.status` with a
  check constraint limited to `REDEEMED` and `CANCELLED`.
- `RewardRedemptionResponse` does not expose `deliveredAt`.
- `ResponsibleDashboardResponse.ResponsibleDashboardRedemption` exposes
  `redeemedAt`, but not status or delivery metadata.
- Mobile `RewardRedemptionStatus` is currently `'REDEEMED'` only, while backend
  already also has `CANCELLED`.
- Mobile `ResponsibleDashboardRedemption` does not include `status` or
  `deliveredAt`.

Planning implication: implement delivery as persistent fulfillment metadata.
Recommended backend shape:

- Add `delivered_at TIMESTAMPTZ` nullable column to `reward_redemptions`.
- Either keep `status = REDEEMED` and derive delivered state from
  `deliveredAt != null`, or add `DELIVERED` to `RewardRedemptionStatus`.
- Preferred for clarity in UI/API: add enum value `DELIVERED` and `deliveredAt`.
  Marking delivered sets `status = DELIVERED` and `deliveredAt = now`.
- Do not write any `CoinTransaction` when marking delivered.
- Make the operation idempotent: marking an already delivered redemption returns
  the existing delivered state without changing `deliveredAt`.
- Add a responsible-only endpoint such as
  `PATCH /reward-redemptions/{id}/delivered` or
  `PATCH /rewards/redemptions/{id}/delivered`. The former is clearer, but it
  introduces a new controller or root route. The planner should align with
  existing controller organization.
- Query by `id` and `familyUnitId` via `RewardRedemptionRepository` to preserve
  tenant isolation.

## Risks and Tradeoffs

| Risk | Why it matters | Planning response |
|------|----------------|-------------------|
| Local-only delivered checkbox | State would disappear on refresh/relogin and mislead the responsible adult | Require backend persistence and integration tests |
| Treating delivery as wallet event | Could duplicate ledger effects or imply coin reversal/credit | Delivery must not touch `Wallet` or `CoinTransaction` |
| Removing `FamilyHub` too aggressively | Existing tests and fallback navigation may break | Plan explicit route updates and navigation tests |
| Remember-me default ambiguity | Current app always persists token | Plan exact checked/unchecked behavior and tests |
| Register screen scope creep | Registration can become onboarding design work | Keep fields to backend `RegisterRequest`: name, email, password, familyName |
| Phase 7 docs drift | API docs already differ from current reward redeem path | Note doc alignment for Phase 7, but update OpenAPI/backend tests for any new endpoint now |

## Suggested Plan Split

### Plan A: Auth entry, register, and remember-me

Scope:
- Add unauthenticated welcome entry with Login and Registro options.
- Add mobile registration path using `POST /auth/register`.
- Add `mantenha-me conectado` checkbox to login.
- Change `AuthContext.login` to persist token only when opted in.
- Preserve restore behavior for stored tokens and clear stored token on logout.

Suggested tests:
- `login-screen.test.tsx` or new auth entry tests for welcome/login/register
  options.
- `auth-context.test.tsx` for remember checked vs unchecked persistence.
- `api-auth.test.ts` for `POST /auth/register` request/response.

### Plan B: Child-first mode switching and dashboard affordances

Scope:
- Change authenticated default entry away from mandatory `FamilyHub`.
- Add `Gerenciar família` in child profile.
- Add `Voltar para o modo criança` in responsible profile when child context is
  available, falling back to child selector when needed.
- Make recent-redemptions dashboard metric/card actionable.
- Keep approval card navigation covered by tests.

Suggested tests:
- `child-navigation.test.tsx` for child profile `Gerenciar família`.
- `responsible-navigation.test.tsx` for return-to-child behavior.
- `responsible-dashboard.test.tsx` for approval and recent-redemption
  affordances.

### Plan C: Delivered reward redemption persistence

Scope:
- Add Flyway migration for `reward_redemptions.delivered_at` and any status
  constraint update if using `DELIVERED`.
- Add domain method on `RewardRedemption` to mark delivered idempotently.
- Add service/controller endpoint for responsible adult to mark delivered.
- Extend `RewardRedemptionResponse` and dashboard redemption DTO with delivery
  metadata.
- Extend mobile API types/service and dashboard cards with checkbox, grey text,
  and `Entregue em: {data}`.

Suggested tests:
- Backend integration test for marking delivered, tenant isolation, idempotency,
  and no extra `CoinTransaction`.
- Responsible dashboard integration test for `deliveredAt` in recent
  redemptions.
- Mobile service test for the mark-delivered endpoint.
- Mobile dashboard test for checkbox, grey/delivered copy, and refresh from API.

## Validation Architecture

Required verification for Phase 06.1:

- Backend: run reward/dashboard integration tests covering delivered redemption
  persistence and dashboard projection.
- Mobile: run focused auth, child navigation, responsible navigation,
  responsible dashboard, and responsible service tests.
- Type safety: run mobile typecheck and backend test compile through the normal
  project commands.
- Manual smoke: start backend and Expo, verify welcome -> login/register,
  remember-me checked/unchecked restart behavior, child mode -> family
  management -> child mode return, approvals link, recent-redemptions focus, and
  delivered checkbox persistence after refresh.
