## Pattern Assignments

### Auth Entry and Registration

Apply to:
- `mobile/src/navigation/routes.ts`
- `mobile/src/navigation/RootNavigator.tsx`
- `mobile/src/features/auth/LoginScreen.tsx`
- `mobile/src/features/auth/AuthWelcomeScreen.tsx`
- `mobile/src/features/auth/RegisterScreen.tsx`
- `mobile/src/features/auth/AuthContext.tsx`
- `mobile/src/features/auth/authService.ts`

Use the current `LoginScreen` form structure: `KeyboardAvoidingView`,
`AppScreen`, visible labels, `TextInput`, inline error, `PrimaryButton`, and
`SecondaryButton`. Use `FamilyHubScreen` only as an analog for two selectable
entry actions, not for the authenticated hub behavior.

Registration must call backend `POST /auth/register`, whose request fields are
exactly `name`, `email`, `password`, and `familyName`. Do not invent invite
code, child fields, or onboarding questions in Phase 06.1.

Session persistence is currently unconditional in `AuthContext.login`. Change
the context API so login receives a remember-session boolean and only calls
`tokenStorage.setToken(token)` when true. Unchecked login keeps the runtime
session in memory and skips SecureStore persistence.

### Child-First Mode Switching

Apply to:
- `RootNavigator.tsx`
- `ChildTabsScreen.tsx`
- `ResponsibleTabsScreen.tsx`
- `ResponsibleProfileScreen.tsx`
- navigation tests

Use current stack route params for `ChildTabs: { child: ChildResponse }`.
Preserve a child context when entering responsible mode from child profile. If
the implementation cannot safely preserve the child through nested responsible
forms, fall back to `ChildProfileSelect` when returning to child mode.

The normal authenticated entry must no longer require the user to choose
between `Sou responsavel` and `Sou crianca`. `FamilyHub` may remain as a
fallback route while tests prove it is not the normal post-login entry.

### Dashboard Affordances

Apply to:
- `ResponsibleHomeScreen.tsx`
- `MetricSummaryCard.tsx`
- `ApprovalCard.tsx`
- responsible dashboard/navigation tests

`ApprovalCard` already exposes `Abrir aprovacoes` and navigates to
`ResponsibleApprovals`; keep this behavior covered by a regression test.

`MetricSummaryCard` is currently static. If it becomes pressable for `Resgates
recentes`, preserve its `minHeight: 88`, two-column wrapping behavior, and
existing value/label hierarchy. The behavior can be implemented as scroll/focus
inside `ResponsibleHomeScreen` or as navigation to a dedicated route, but tests
must prove the user can reach the recent redemptions section from the metric or
card.

### Delivered Reward Redemptions

Apply to backend rewards/dashboard files and mobile responsible dashboard.

Current backend status values are `REDEEMED` and `CANCELLED`, with a database
check constraint in `V3__create_reward_schema.sql`. Delivery must be a new
persistent fulfillment state, not local-only UI. Preferred shape:

- add nullable `delivered_at TIMESTAMPTZ`;
- add enum value `DELIVERED`;
- update the status check constraint in a new Flyway migration;
- `markDelivered()` sets status to `DELIVERED` and `deliveredAt` once;
- repeated mark-delivered calls return the existing `deliveredAt`;
- no `Wallet` or `CoinTransaction` mutation occurs.

Expose delivery metadata in `RewardRedemptionResponse` and
`ResponsibleDashboardResponse.ResponsibleDashboardRedemption`; mirror it in
`mobile/src/api/types.ts`.

Use a checkbox row in mobile with `accessibilityRole="checkbox"` and
`accessibilityState={{ checked }}`. A delivered card keeps its dimensions,
changes title/meta text to `textMuted`, and shows `Entregue em: {data}` from
backend data.

## Test Patterns

- Mobile auth tests live under `mobile/src/features/auth/__tests__`.
- Mode/navigation tests live under child/responsible `__tests__` folders and
  mock navigation with `navigate = jest.fn()`.
- Mobile service tests should assert paths/methods and that `familyUnitId` is
  not present in path/body.
- Backend integration tests should use the existing `registerToken`,
  `createChild`, `createReward`, and `creditWallet` helper style in
  `RewardRedemptionIntegrationTest`.
- Tenant isolation tests should create two families and assert not found or
  absent data for cross-family access.
