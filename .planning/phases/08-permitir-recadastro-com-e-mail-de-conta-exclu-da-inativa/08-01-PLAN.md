<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public auth API -> account history | Login, registration, and reset must not reveal whether an inactive historical account exists. |
| JWT token -> active user/family state | Old tokens contain old IDs, so protected operations must keep checking active user/family state. |
| Migration -> production data | Schema migration must not silently mutate or choose winners among duplicate active accounts. |
| Demo seed -> historical demo data | Seed must distinguish active demo account from inactive historical demo rows. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01-01 | Information Disclosure | Login/reset/register API | High | mitigate | Return existing public errors/responses only: `INVALID_CREDENTIALS`, enumeration-safe reset accepted, normal registration success for inactive-only duplicate. |
| T-08-01-02 | Elevation of Privilege | Old JWT after deletion | High | mitigate | Preserve active-user checks and deactivate old `AppUser`; do not add restoration path. |
| T-08-01-03 | Tampering | Migration over account rows | High | mitigate | Migration fails on duplicate active normalized e-mails and never rewrites historical e-mails. |
| T-08-01-04 | Spoofing | Active duplicate e-mail registration | High | mitigate | PostgreSQL partial unique index on `lower(email) WHERE active = true` plus service-level conflict check. |
| T-08-01-05 | Repudiation | Account deletion history | Medium | mitigate | Soft deactivate user/family while preserving historical rows and reset-token invalidation. |
</threat_model>
