<objective>
Implementar o fluxo backend de solicitação e confirmação por e-mail para exclusão física de todas as contas históricas associadas ao e-mail normalizado.
</objective>

<scope_note>
Este plano mantém request/token/purge juntos porque o token precisa ser bloqueado e consumido na mesma transação que captura todas as contas e executa o purge; separar essas etapas criaria uma janela de replay ou confirmaria um token sem garantir a exclusão. A migration, sender, controller e testes são partes do mesmo contrato destrutivo.
</scope_note>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public e-mail request -> account lookup | Entrada arbitrária deve ser enumeration-safe. |
| E-mail token -> destructive confirmation | Token é a prova de posse do e-mail e precisa ser dedicado, expirável e single-use. |
| Service -> PostgreSQL | SQL destrutivo deve ser parametrizado, ordenado e transacional. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|---|
| T-09-01 | Information Disclosure | Request endpoint | mitigate | Resposta uniforme e nenhum token no HTTP. |
| T-09-02 | Spoofing/Tampering | Permanent token | mitigate | Purpose dedicado, hash, expiração, uso único e e-mail correspondente. |
| T-09-03 | Tampering | Multi-family purge | mitigate | IDs derivados do e-mail confirmado e transação JDBC FK-safe. |
| T-09-04 | Repudiation | Rollback/logs | mitigate | Failure injector determinístico, rollback PostgreSQL e logs sem segredos. |
</threat_model>
